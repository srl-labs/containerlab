# Release 0.81

:material-list-status: [Full Changelog](https://github.com/srl-labs/containerlab/releases)

/// danger | Breaking changes: node `extras` removed
The `extras` node field is removed. Every key it carried either moved to a [kind-specific config](../manual/nodes.md#kind-specific-config) key — set directly on the node definition — or was dead code and is dropped. A topology that still sets `extras` fails to parse with a pointer to the kind-specific config documentation.
///

## Removed node extras

The `extras` node field predates the kind-specific config mechanism introduced in 0.80, and everything it carried was either kind-specific or dead. With kind-specific config the proper home for kind-owned keys, `extras` is gone and its keys are set directly on the node definition:

| old key | new key | where |
|---|---|---|
| `extras.frr.daemons` | `daemons` | `frr`/`frrouting` kinds |
| `extras.ceos-copy-to-flash` | `copy-to-flash` | `arista_ceos` kind |
| `extras.k8s_kind.deploy.kubeconfig` | `kubeconfig` | `k8s-kind` kind |
| `extras.k8s_kind.deploy.wait` | `wait` | `k8s-kind` kind |

For example, a lab that selected the FRR daemons with `extras`:

```yaml
topology:
  nodes:
    r1:
      kind: frr
      extras:
        frr:
          daemons: [ospfd, bgpd]
```

now sets the `daemons` key on the node definition:

```yaml
topology:
  nodes:
    r1:
      kind: frr
      daemons: [ospfd, bgpd]
```

The migrated keys participate in the regular node > group > kinds > defaults inheritance, are validated per kind, and are modeled in the JSON schema. Magic variables are resolved in kind-specific config values, as they were in `extras`.

Two keys are dropped without replacement:

* `extras.srl-agents` — the SR Linux agent spec copy into the node's `appmgr` directory was removed in 0.74, leaving the key as a silent no-op in the Docker runtime.
* `extras.mysocket-proxy` — no consumer; the mysocketctl/border0 integration is long gone.

## C9s runtime decoupling

The topology compiler that renders a containerlab definition into c9s Node, Link, and NodeProfile primitives moved from the [clabernetes](https://github.com/clabernetes/clabernetes) repository into containerlab itself, where the topology semantics it renders live. The dependency now points one way — only clabernetes depends on containerlab — and both the `c9s` runtime and the c9s controller compile with the same engine. Update clabernetes and containerlab together when upgrading a c9s deployment.
